# Импорт Stanford PLY через VTK

## Статус

Добавлен код импорта и диагностики. Конфигурация CMake, сборка, запуск и тесты не выполнялись: проверку выполняет пользователь. Установка VTK автоматически не производится.

Модуль `PostTopOptVtk` подключается опцией `POSTTOPOPT_WITH_VTK=ON`; по умолчанию выключен. Требуется установленная VTK 9 с модулями CommonCore, CommonDataModel, FiltersCore, IOPLY, собранная для того же компилятора и архитектуры, что и PostTopOpt. Сборку VTK для MSVC нельзя использовать с MinGW.

## Архитектура

- `include/PlyImporter.h` — результат импорта: Mesh, AABB, исходные количества точек/полигонов и диагностика рёбер; публичный API не содержит типов VTK.
- `src/PlyImporter.cpp` — vtkPLYReader → vtkTriangleFilter → Mesh. Ошибки VTK преобразуются в исключения. Для подсчёта граничных рёбер и рёбер с более чем двумя смежными гранями используется vtkFeatureEdges.
- `examples/ply_import.cpp` — ручная программа диагностики и необязательного OBJ-экспорта. Без входных аргументов обходит только PLY непосредственно в examples; вложенные каталоги, включая _old, не обрабатываются. Каждый файл обрабатывается отдельно; ошибка одного не останавливает остальные и приводит к итоговому коду 1.

Координаты и единицы сохраняются. Автоматического заполнения отверстий, слияния точек, переориентации, сглаживания и нормализации нет. Цвета, confidence и прочие атрибуты PLY не переносятся в Mesh.

Признак `closed_by_edge_incidence` означает только отсутствие граничных и неманифолдных рёбер после триангуляции. Он не доказывает многообразность в вершинах, согласованность ориентации, отсутствие вырожденных граней или самопересечений. Это не разрешение автоматически считать модель корректной границей объёма.

## Команды для ручной проверки

В терминале с настроенным компилятором и VTK; VTK_DIR должен указывать на каталог с VTKConfig.cmake. Для MinGW:

```powershell
cmake -S . -B build-vtk -G "MinGW Makefiles" -DPOSTTOPOPT_WITH_VTK=ON -DBUILD_TESTING=OFF -DVTK_DIR="C:/path/to/vtk/lib/cmake/vtk-9.x"
cmake --build build-vtk --target PostTopOptPlyImport
.\build-vtk\PostTopOptPlyImport.exe --help
.\build-vtk\PostTopOptPlyImport.exe examples/bun_zipper.ply
# Все PLY непосредственно в examples:
.\build-vtk\PostTopOptPlyImport.exe
# Экспорт без перезаписи существующего OBJ:
.\build-vtk\PostTopOptPlyImport.exe examples/Armadillo.ply --output-dir results/ply-import
```

Для MSVC использовать отдельный каталог и генератор Visual Studio; исполняемый файл обычно находится в подкаталоге выбранной конфигурации. DLL VTK должны быть доступны при запуске.

При проверке нужны отчёты по всем четырём моделям. Дополнительно следует вручную проверить ошибку отсутствующего файла и отказ при повторном экспорте в существующий OBJ. Эти проверки не запускались.

## Следующий этап

Преобразование импортированной поверхности в поле расстояний и извлечение DC/MC в этом этапе не реализованы. Перед добавлением vtkImplicitPolyDataDistance необходимо определить требования к замкнутости, ориентации, единицам, области и разрешению сетки. У открытой или некорректно ориентированной поверхности знак псевдорасстояния не следует интерпретировать как надёжную классификацию внутренней области. Восстановление отверстий требует отдельного решения и не должно молча менять эталон.

## Переход PLY → поле расстояний → извлечение

Добавлен `PlyDistanceField` и ручная программа `PostTopOptPlyExtract`. Код нового этапа не собирался и не запускался. Ранее пользователь подтвердил успешный импорт четырёх моделей: Armadillo и Happy Buddha без граничных рёбер, Bunny с 223 и Dragon с 4270 граничными рёбрами. Это результаты проверки рёбер, не полная валидация поверхности.

Адаптер использует существующий импорт, отклоняет открытые и неманифолдные по рёбрам поверхности и треугольники нулевой площади. На отдельной VTK-копии выполняется согласование ориентации через vtkPolyDataNormals, затем создаётся vtkImplicitPolyDataDistance. Исходный PLY не меняется, отверстия не заполняются. Публичная Field захватывает VTK-объект с управлением временем жизни. Обращения к ней предполагаются последовательными: потокобезопасность не заявляется.

Автоориентация не заменяет проверку самопересечений, многообразия в вершинах и вложенных оболочек/полостей. Для последних требуется отдельная политика знака. Проверка положительного значения поля в восьми углах AABB обнаруживает только очевидные ошибки знака.

Для длиннейшей стороны исходного AABB длины L и разрешения N шаг равен $h=L/N$. По каждой оси добавляется запас в три ячейки с обеих сторон; число ячеек округляется вверх. Координаты и единицы модели сохраняются. `--cells` задаёт N без запаса, поэтому полное число ячеек вдоль длиннейшей стороны обычно равно N+6.

Поддержаны dc, emilk, mc. CGAL в этом примере не подключён, чтобы не использовать VTK callback в потенциально параллельном backend без отдельной проверки. Для DC сохраняются текущие параметры ContourOptions: регуляризация 0.001, ограничение ячейкой и бисекция. Градиенты вычисляются существующим кодом центральными разностями с шагом $10^{-3}h$; параметр является начальной настройкой, не оптимизированной по метрикам. Вблизи рёбер исходной полигональной поверхности поле негладкое, поэтому результат чувствителен к шагу и разрешению.

Сетка и время подготовки/извлечения выводятся в консоль. При существующем выходном OBJ программа отказывается перезаписывать его. Геометрические ошибки, топология и самопересечения результата автоматически не измеряются. Лимит разрешения API — 4..512; высокие значения могут потребовать значительного времени и памяти. Начальная проверка — 32 ячейки на длиннейшую сторону Armadillo.

### Ручная проверка пользователем

PowerShell из корня проекта, с VTK UCRT64 и соответствующим компилятором:

```powershell
$env:PATH = "C:\msys64\ucrt64\bin;$env:PATH"
cmake -S . -B build-vtk -DPOSTTOPOPT_WITH_VTK=ON -DBUILD_TESTING=OFF -DVTK_DIR=C:/msys64/ucrt64/lib/cmake/vtk
cmake --build build-vtk --target PostTopOptPlyExtract -j 4
.\build-vtk\PostTopOptPlyExtract.exe examples/Armadillo.ply --cells 32 --method dc
```

Ожидаемый путь результата: `results/stanford/Armadillo_dc_32.obj`. Следующие отдельные прогоны: 64 ячейки; методы emilk и mc на том же разрешении; Happy Buddha. Bunny/Dragon должны отклоняться до появления отдельно согласованного способа обработки отверстий. Для повторения запуска указать новый `--output`.

После успешной сборки пользователь проверяет непустой результат и совмещение исходной/восстановленной моделей в просмотрщике. Знак внутри тела, замкнутость и точность требуют отдельных проверок и не подтверждены самим фактом создания OBJ.
