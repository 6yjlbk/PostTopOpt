# Запуск и чтение результатов

Основная программа — `PostTopOptRun`. Для всех источников одинаковы выбор метода, режим benchmark, отчёты и экспорт. Команды ниже предназначены для PowerShell из корня проекта.

## Сборка

```powershell
cd "C:\Users\Gleb\Documents\VS Code\APM\PostTopOpt"
$env:PATH="C:\msys64\ucrt64\bin;$env:PATH"
cmake --preset release
cmake --build --preset release
```

Полная пересборка: `cmake --build --preset release --clean-first`. Для Debug использовать `cmake --preset debug` и `cmake --build --preset debug`.

Локальные presets рассчитаны на MSYS2 UCRT64 в `C:/msys64`, GCC/MinGW и установленные SDK CGAL, ParaView и VTK. Eigen 3.4.1 загружается CMake при конфигурации. На другой машине нужно проверить пути и совместимость SDK с компилятором. При включённом ParaView PLY-модуль должен использовать совместимую с ним VTK; смешивать произвольные сборки VTK и ParaView нельзя.

`build/release` и `build/debug` — рабочие каталоги. `build/legacy` — архив перенесённых кэшей с устаревшими абсолютными путями; его нельзя использовать как действующую сборку.

## Одинаковый запуск для трёх источников

```powershell
# PLY: получить VF и сравнить DC с ParaView.
.\build\release\PostTopOptRun.exe --input data/models/Armadillo.ply --cells 64 --method compare --output-dir results/armadillo-64

# Аналитическая фигура: создать VF и выполнить то же сравнение.
.\build\release\PostTopOptRun.exe --input gyroid --cells 64 --complexity 4 --method compare --save-volume data/volumes/gyroid-64.csv --output-dir results/gyroid-64

# Готовые VF: загрузить без повторного создания геометрии.
.\build\release\PostTopOptRun.exe --input data/volumes/gyroid-64.csv --method compare --output-dir results/gyroid-loaded
```

Выходной каталог должен быть новым или пустым. Существующие результаты не перезаписываются. CSV входных VF сохраняется только при `--save-volume`; для этого также нужен новый путь.

| Параметр | Значение и смысл |
| --- | --- |
| `--input` | PLY, CSV, PTOV1 или имя аналитической фигуры |
| `--output-dir` | Обязательная папка результатов |
| `--method dc` | Только собственный DC; это метод по умолчанию |
| `--method paraview-amr` | Только ParaView |
| `--method compare` | DC и ParaView на одном массиве VF |
| `--method all` | dc, emilk, mc, cgal-dc, paraview-amr; нужны все backend |
| `--cells 64` | Разрешение для PLY или аналитического задания, диапазон 16–500 |
| `--complexity 4` | Частота четырёх периодических заданий, диапазон 1–12 |
| `--threshold 0.5` | Порог материала, строго между 0 и 1 |
| `--width-cells 2` | Ширина перехода SDF → VF для PLY в шагах сетки, диапазон (0,4] |
| `--benchmark true` | По умолчанию включён; включает прогрев, повторы и профиль |
| `--repeats 5` | Число измеряемых повторов на метод, диапазон 2–50 |
| `--export true` | По умолчанию включён; сохраняет OBJ |
| `--save-volume path.csv` | Дополнительно сохранить подготовленный массив VF |

Для аналитического банка `cells=N` означает $N^3$ элементов в области $[-1,1]^3$. Для PLY — разрешение вдоль самой длинной стороны исходного AABB; добавляется запас по три ячейки с каждой стороны. Итоговые размеры по осям могут различаться и превышать заданное `cells`.

Загрузка CSV/PTOV1 ограничена суммарным числом $500^3$ элементов. Это ограничение приложения, не математический предел DC. Сохранённый файл уже задаёт сетку, поэтому при его загрузке `--cells` и `--complexity` не указываются.

Имена фигур: `sphere`, `torus`, `sphere-union`, `drilled-box`, `cone`, `gyroid`, `channels`, `lattice`, `shells`. `complexity` влияет только на последние четыре. Размеры простых фигур фиксированы в `apps/AnalyticModels.cpp`. Формулы старых примеров в `apps/legacy` сохранены отдельно и могут иметь другие масштабы.

Настройки собственного DC можно указать явно:

```powershell
.\build\release\PostTopOptRun.exe --input sphere --cells 64 --method dc --lambda 0.001 --regularization true --constrained true --bisection true --cache true --qef true --output-dir results/sphere-dc
```

`--cache false` отключает Hermite-кэш, `--qef false` выбирает контрольный QEF-решатель. `lambda` и включение регуляризации относятся к собственным DC; CGAL и ParaView используют свои решатели. Булевы параметры принимают `true/false` или `1/0`.

## Обычный запуск и benchmark

Чтобы только построить и сохранить сетку:

```powershell
.\build\release\PostTopOptRun.exe --input data/models/Armadillo.ply --cells 64 --method compare --benchmark false --output-dir results/armadillo-meshes
```

При `benchmark=false` каждый выбранный метод выполняется **ровно один раз**, `--repeats` игнорируется, `summary.csv` и `runs.csv` не создаются. Сохраняются `settings.txt` и, если экспорт включён, OBJ.

При `benchmark=true` программа:

1. Один раз готовит общий массив VF.
2. Делает один прогревочный вызов каждого метода вне статистики.
3. Выполняет заданное число измеряемых повторов, меняя порядок методов между повторами.
4. Отдельно вызывает каждый метод с профилированием и экспортирует его результат. Этот вызов не входит в статистику обычного времени.

Повторы нужны для устойчивой оценки скорости, а не для улучшения сетки. Все пять повторов 0–4 сохраняются в **один** `runs.csv`; при двух методах в нём десять строк данных.

## Что находится в папке результата

```text
results/armadillo-64/
├── settings.txt       источник, сетка, порог и настройки
├── summary.csv        итоговые метрики: методы по столбцам
├── runs.csv           измерения отдельных повторов
├── dc.obj
└── paraview-amr.obj
```

Все времена в отчётах и консоли — **секунды с тремя знаками после десятичной точки**. CSV разделяется запятыми; десятичный разделитель — точка. В `summary.csv` первые столбцы `metric` и `description` задают идентификатор и русское описание, остальные — методы. Файл имеет UTF-8 BOM для корректного чтения описаний в Excel.

### Основные времена

| Метрика | Что измеряется |
| --- | --- |
| `preparation_vf_s` | Время от начала main до готовой сетки и проверенного массива VF, включая разбор параметров, чтение или генерацию |
| `isosurf_median_s` | Медианное время одного построения изоповерхности из готовых VF |
| `isosurf_min_s - isosurf_max_s` | Диапазон времён повторов, например `1.661 - 1.706` |
| `build_isosurf_s` | Подготовка VF + медианное время построения |
| `algorithm_without_vf_s` | Явная итоговая строка без подготовки VF; совпадает с `isosurf_median_s` |
| `algorithm_with_vf_s` | Явная итоговая строка с подготовкой VF; совпадает с `build_isosurf_s` |
| `export_s` | Время записи OBJ |
| `profile_isosurf_s` | Полное время отдельного вызова с подробным профилем |

В `runs.csv` время конкретного повтора называется `isosurf_s`. Медиана — центральное значение отсортированных времён; она меньше зависит от единичного замедления компьютера, чем максимум.

**Время построения включает весь публичный `extract`**: реконструкцию поля, узловые значения, пересечения и нормали, QEF, связность, выделения памяти и внутренние адаптеры до готового `Mesh`. Проверка результата, уничтожение Mesh и запись OBJ находятся за пределами этого замера.

Для ParaView в построение входят создание VTK-данных, фильтр и преобразование результата в `Mesh`. Подготовка VF из PLY в это время не входит. `preparation_vf_s` общая для методов, поэтому она повторяется в их столбцах.

Суммы `build_isosurf_s` и `algorithm_with_vf_s` — расчётное время одного прохода, а не длительность всего процесса с прогревами и повторами. Сохранение входного CSV и экспорт OBJ в них не входят.

### Подробный профиль

| Метрика | Этап |
| --- | --- |
| `sampling_s` | Вычисление значений VF-поля в узлах для собственного DC |
| `hermite_s` | Обход ячеек, пересечения рёбер, нормали и работа кэша |
| `qef_s` | Размещение вершин решением QEF |
| `connectivity_s` | Построение граней |
| `vtk_preparation_s` | Подготовка VTK-структур, не исходных VF |
| `filter_s` | Работа фильтра ParaView |
| `conversion_s` | Преобразование результата ParaView в Mesh |

Мелкие таймеры добавляют накладные расходы. Поэтому профиль измеряется отдельно, а сумма его этапов не обязана совпадать с обычной медианой или даже покрывать весь диагностический вызов: часть накладных расходов не размечена.

Число вершин, quads и triangles описывает размер сетки. Счётчики собственного DC помогают понять расходы: `field_queries` — запросы поля; `active_cells` — ячейки с выходной вершиной; `edge_visits` — посещения пересечённых рёбер; `unique_edges` — уникальные внутренние пересечённые рёбра; `hermite_evaluations` и `hermite_cache_hits` — вычисления и попадания в кэш; `qef_interior` и `qef_boundary` — ранние возвраты и поиски на границе.

`unique_edges` не учитывает рёбра границы области. На банке с пустым внешним запасом это не мешает сравнению, но для произвольного поля нельзя автоматически приравнивать этот счётчик всем вычисленным пересечениям.

Пустая ячейка означает неприменимый показатель или отключённый экспорт. Для MC и CGAL внутреннее профилирование не реализовано: есть общее время и размеры Mesh, а этапы пусты. Наличие одинаковых столбцов не означает наличия одинаковых внутренних алгоритмов.

## Формат сохранённых VF

Новый формат — CSV версии 1. Старый текстовый PTOV1 по-прежнему читается.

```text
PostTopOptVolume,1
cells,Nx,Ny,Nz
origin,Ox,Oy,Oz
spacing,Hx,Hy,Hz
x,y,z,rho
0,0,0,0.5
...
```

Значения относятся к центрам элементов, записываются в порядке z-fastest с 17 значащими цифрами. Имя `rho` в формате означает VF. CSV описывает конкретный массив и его геометрию, а не аналитическую формулу фигуры. Округление времён до трёх знаков на точность сохраняемых VF не влияет.

## Проверки

```powershell
ctest --preset release
# Только численные и API-проверки:
ctest --test-dir build/release --output-on-failure -R '^(DualContouringTest|ExtractionMethodsTest|CgalBackendTest|ArchitectureApiTest|OptimizationRegressionTest|ApplicationDataTest)$'
```

Тесты проверяют численные случаи, API, CSV и регрессии оптимизаций. Они не доказывают отсутствие дефектов на любой поверхности. Старые интеграционные примеры записывают артефакты в каталог сборки `test-results`.
